# VoiceLine Local35 추가 점검과 개선 제안

점검일: 2026-10-31  
대상: `VoiceLine_AndroidStudio_Local35_Metronome_Warmup.zip`  
버전: `2.0.0-local35`, versionCode `50`

최신 프로젝트의 100개 파일을 배포 ZIP과 비교한 뒤 점검했습니다. 기존 119개 검사는 다시 모두 통과했습니다. 아래는 추가로 확인한 조건과 개선 제안이며, 이번 점검에서 프로젝트 소스는 변경하지 않았습니다.

현재는 기능을 많이 늘리기보다 **확인된 예외 처리 보완 → 구식 코드 정리 → 긴 기록의 성능 개선 → 실기기 확인** 순서가 좋습니다.

## 1. 먼저 보완할 항목

| 순서 | 항목 | 확인 범위 | 사용자 영향 |
|---|---|---|---|
| 1 | 예비 피아노 경로의 없는 OGG 파일 참조 | 실제 코드와 포함 파일 대조, 실패 응답 주입 | 음원 준비 실패/준비 중에 불필요한 요청과 일관되지 않은 상태 표시 |
| 2 | 복구 정보 손상과 녹음 중 상태 구분 | 실제 Java 파일 저장소에 손상된 보조 정보 주입 | 음성 파일은 남아 있어도 미완료 녹음 목록에 보이지 않을 수 있음 |
| 3 | 1초 미만 녹음의 그래프 시간축 통일 | 실제 그래프 함수에 0.5초 자료 주입 | 음정 곡선과 재생 위치선의 가로 위치가 다름 |
| 4 | 긴 녹음 그래프의 배경 계산·캐시 | 실제 재생/그리기 경로 검토 | 긴 녹음에서 필요 이상의 반복 계산과 객체 생성 |
| 5 | 극단적인 메트로놈 설정의 처리량 제한 | 실제 스케줄러에 특수 설정 주입 | 지나치게 빠른 클릭 생성으로 오디오 처리 부담 가능 |

실기기에서의 발생 빈도나 성능 저하 정도는 측정하지 않았습니다. 조건 재현과 실제 휴대폰 발생을 구분해야 합니다.

### 1-1. 예비 음원에 이전 OGG 파일 경로가 남아 있습니다

관련: `piano.js:359`, `:408`, `:430`, `:465`, `:478`

현재 APK에 포함되는 음원은 `vendor/salamander`의 MP3 28개입니다. 그런데 기존 예비 음원 로더는 다음과 같은 이전 경로를 만듭니다.

`./samples/piano/INSPiano_Vel01_C4_01.ogg`

이 파일과 `samples/piano` 음원 묶음은 현재 프로젝트에 없습니다. 주 피아노 엔진이 준비되지 않았을 때 이 예비 경로가 호출될 수 있습니다.

**재현:** 실제 로더에 404 응답을 넣었습니다. 상태가 `기본 음색 사용 · 음원 오류`에서 `피아노 음원 일부 미지원`으로 바뀌었습니다. 예비 로더가 주 엔진의 오류 안내를 덮어씁니다.

**수정 방향:** 포함된 MP3에 맞춰 예비 샘플 경로를 통일하거나, 예비 경로를 명확한 합성음으로 단순화해야 합니다. 상태 표시도 엔진 한 곳에서 관리하는 것이 좋습니다. 오래된 OGG용 보정값과 관련 주석은 경로 정리와 함께 검토해야 합니다.

이것이 주 피아노 MP3 파일이 빠졌다는 뜻은 아닙니다. 기존 합성음 예비 경로도 있으므로 이 조건만으로 소리가 전혀 나지 않는다고 단정하지 않습니다.

### 1-2. 복구 정보가 잘못되면 파일이 목록에서 조용히 빠집니다

관련: `NativeWavStore.java:115`, `:132–139`

미완료 파일 목록을 만드는 함수는 예외를 모두 같은 방식으로 무시합니다. 현재 녹음 중이라 아직 읽을 수 없는 파일과, 보조 정보가 손상됐거나 파일 접근에 실패한 경우를 구분하지 않습니다.

**재현:** 실제 파일 저장소로 16kHz·1초 WAV를 만들었습니다. 음성 파일은 32,044바이트로 그대로 두고 보조 정보의 입력 속도 값만 잘못된 문자열로 바꿨습니다. 그 뒤 목록 함수는 빈 목록을 반환했습니다.

- 손상 전: 복구 목록에 표시
- 손상 후: 복구 목록에 표시되지 않음
- WAV 파일: 그대로 존재

**수정 방향:** 녹음 중인 파일만 잠시 제외하고, 손상·접근 실패는 오류 항목으로 보여줘야 합니다. WAV 헤더가 정상인 경우에는 표본 속도와 길이를 다시 읽어 복구 정보를 재구성하는 방법도 검토할 수 있습니다.

보조 정보 손상은 의도적으로 만든 조건입니다. 정상 녹음에서 항상 발생하거나 이미 사용자의 녹음이 손상됐다는 의미는 아닙니다.

### 1-3. 1초 미만 녹음의 그래프와 재생 위치선이 어긋납니다

관련: `piano.js:2819`의 `drawHistoryPitch()`

음정 점의 가로축에는 최소 1,000ms를 적용하지만, 재생 위치선은 실제 오디오 길이를 사용합니다. 길이가 1초 이상일 때는 이 차이가 드러나지 않습니다.

**재현:** 길이 0.5초, 마지막 음정 점 500ms, 캔버스 폭 600px 조건에서 다음을 확인했습니다.

| 항목 | X 위치 |
|---|---:|
| 마지막 음정 점 | 330.5px |
| 파일 끝의 재생 위치선 | 592px |
| 차이 | 261.5px |

**수정 방향:** 곡선과 재생 위치선이 같은 시간 범위를 사용하도록 맞추면 됩니다. 아주 짧은 녹음의 길이 표시도 소수점 초 등으로 구분하면 이해하기 쉽습니다.

이는 그래프 표시 문제이며 녹음 파일이 나뉘거나 음성이 사라지는 문제는 아닙니다.

### 1-4. 긴 녹음의 곡선을 매번 전부 다시 계산합니다

관련: `piano.js:2819`, `:2885`

목록용 작은 메타데이터 분리는 이미 적용되어 있습니다. 추가로 개선할 곳은 재생 그래프입니다.

재생 중에는 약 90ms 이상 간격으로 그리기를 다시 하면서 전체 음정 배열을 필터링하고, 음역을 다시 계산하고, 새 점 객체 배열을 만든 뒤 전체 곡선을 그립니다. 현재 구조에서는 노란 재생선만 이동해도 배경 곡선 계산이 반복됩니다.

**개선 방향:**

- 곡선·음역·눈금은 재생 시작 또는 크기 변경 때 계산해 캐시합니다.
- 화면 픽셀 수에 맞춰 표시할 점을 줄이되 무음 구간과 최저·최고 변화는 보존합니다.
- 반복 프레임에서는 재생 위치선만 갱신합니다.

현재 휴대폰에서 프레임 저하를 측정한 결과는 아닙니다. 불필요한 반복 작업이 있는 접근 경로를 확인한 것입니다.

### 1-5. 메트로놈 설정 조합의 클릭 속도 상한이 필요합니다

관련: `metronome.js:11`, `:20`, `:70`

각 설정 값은 유효 범위로 제한하지만, BPM·기준 음표·분모·세분을 조합했을 때의 최종 클릭 속도는 제한하지 않습니다.

**재현 조건:** 300 BPM, 분모 64, 점4분음표 기준, 8분할.

- 계산된 클릭: 초당 960회
- 초기 예약: 오실레이터 73개 생성
- 다음 100ms 동안 추가 예약: 96개 생성

**개선 방향:** 박자표 자체를 없애기보다, 실제 클릭 간격이 지나치게 짧아지는 조합을 안내하거나 세분 클릭을 줄이는 보호가 좋습니다. 일반적인 박자와 빠르기의 동작은 유지해야 합니다.

이는 특수 설정에서 생성되는 작업 수를 확인한 것입니다. 실기기에서 앱 종료나 오디오 오류가 발생했다고 주장하는 결과는 아닙니다.

## 2. 불필요하거나 정리할 코드

| 대상 | 확인한 내용 | 정리 방향 |
|---|---|---|
| 이전 OGG 예비 로더·보정표·주석 | 포함 파일과 맞지 않는 경로가 존재 | 주 엔진/예비 음색의 역할을 정한 뒤 관련 코드 정리 |
| 이전 워밍업 캔버스 표시 | 새 워밍업 안내를 그린 뒤 먼저 반환하는데, 아래에 이전 워밍업 그리기 분기가 남아 있음 | 기존 워밍업 그래프 분기와 전용 표시 조건 제거 |
| 사용하지 않는 샘플 목록 상수 | `ACOUSTIC_SAMPLE_MIDI`는 선언 뒤 참조가 없음 | 예비 경로 정리와 함께 제거 검토 |
| 불필요한 훈련 상태값 | `lastPlayed`, `relativeChanges`, `clicks`, 세션의 `phase`·`done` 등은 현재 판정/표시에서 사용하지 않음 | 동작과 검사 확인 후 제거 |
| 결과에서 쓰지 않는 누적값 | `latestRms`, `totalRms`, `rmsMin` 등은 기록·표시·판정에서 읽지 않는 값이 남아 있음 | 실제 필요한 통계만 유지 |
| CSS의 누적 덮어쓰기 | 여러 버전의 화면 규칙이 뒤에 계속 추가됨 | 모드별/화면 크기별 규칙으로 통합; 반응형 규칙을 일괄 삭제하면 안 됨 |
| 큰 핵심 JS 파일 | `piano.js` 2,978줄에 저장·오디오·훈련·화면 처리가 모임 | 녹음/저장, 훈련, 기록 화면, 피아노 엔진 단위로 점진적으로 분리 |

**삭제하면 안 되는 항목도 있습니다.** 기존 녹음 Blob 재생, Local32/33의 임시 PCM 복구, 기록 마이그레이션은 구 버전 데이터를 위해 여전히 필요합니다. 브라우저용 마이크·녹음 예비 경로도 웹 지원을 유지한다면 필요합니다. 음원과 라이선스 파일, 아이콘 원본 역시 단순히 참조 횟수만 보고 삭제하면 안 됩니다.

## 3. 추가하면 실용적인 기능

메인 가로 화면에 버튼을 계속 늘리기보다 기존 설정창과 기록 화면 안에서 제공하는 방향이 좋습니다.

| 추천 순서 | 기능 | 필요한 이유 | 배치 제안 |
|---|---|---|---|
| 1 | 저장 공간과 예상 녹음 가능 시간 | WAV는 44.1kHz·16비트·모노 기준 1시간 약 318MB이므로 공간 확인에 도움 | 녹음 설정/기록 화면에 작은 정보로 표시 |
| 2 | 녹음 이름 변경과 검색 | 현재 녹음 제목이 동일해 파일이 많아지면 날짜만으로 찾기 어려움 | 녹음 기록의 메뉴·검색창 |
| 3 | 메트로놈 설정 즐겨찾기 | BPM·박자·강세 묶음을 반복해서 맞출 필요가 줄어듦 | 박자·음량 설정창에서 이름을 붙여 저장/불러오기 |
| 4 | 워밍업 단계별 시간과 안내음 설정 | 들이쉬기·내쉬기·허밍·쉬기 시간, 소리 켜기/끄기를 선택할 수 있음 | 워밍업 설명 옆 설정창; 기본값은 현재 4/6/6/3초 유지 |

추가 사용성 개선으로는 **메트로놈 음량만 바꿀 때 박을 유지**하는 방법도 좋습니다. 현재는 모든 소리 설정 변경이 같은 재시작 경로를 사용하므로 음량을 바꿔도 첫 박부터 다시 시작합니다. 현재 안내와 일치하는 동작이지만 사용성은 더 다듬을 수 있습니다.

녹음 내보내기·기록 비교, 클라우드 동기화, 탭 템포, 세로 모드와 화면 확대는 이번 추천 범위에 넣지 않았습니다. 앞서 정한 기능 범위와 가로 화면의 단순한 구성을 유지하는 편이 좋습니다.

## 4. 코드 검사 외에 필요한 확인

**119개 검사 통과는 실제 APK·화면·마이크 검증을 대신하지 않습니다.** 지금까지의 Java 검사는 API 스텁 또는 실제 파일 입출력 검사이며 Android SDK 빌드는 수행하지 않았습니다.

사용 중인 Galaxy S24 Ultra / Android 16에서 우선 확인할 내용은 다음과 같습니다.

1. 가로 화면에서 기본·확대 글꼴과 키보드가 열린 상태의 잘림/스크롤.
2. 메트로놈 켜기/끄기, 설정창 뒤로가기, 64박 페이지 이동, 화면 잠금 뒤 예약 클릭 취소.
3. 워밍업 허밍 시작·종료의 화면과 안내음, 전화/오디오 중단 후의 재개·중지.
4. 녹음 시작·끝 음절, 무음 포함 10~30분 녹음, 전체 재생과 구간 이동.
5. 저장 공간 부족과 앱 중단 후의 복구 목록·재시도.

자동 검사는 실제 HTML 렌더링 및 Android 브리지·파일 재생까지 이어지는 통합 검사로 보강하는 것이 좋습니다. 포함 음원과 예비 로더의 경로 일치 검사도 추가해야 합니다.
