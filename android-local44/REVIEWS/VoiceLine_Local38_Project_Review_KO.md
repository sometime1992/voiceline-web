검토일: 2026-10-31  
대상: VoiceLine_AndroidStudio_Local38_Help_Quick_Reset.zip  
앱 버전: 2.0.0-local38 / versionCode 53

현재 우선순위는 **녹음 복구·외부 보관 → 음원·재생 표시 오류 → 긴 기록 성능 → 코드 정리·실기기 검증**입니다. 기능을 더 늘리기 전에 아래 예외 처리를 보완하는 것이 좋습니다.

- 최신 배포 ZIP의 110개 파일과 작업 원본이 일치함을 확인했습니다.
- Android 네이티브 마이크·WAV 저장·재생 범위 요청, JavaScript 녹음·기록·훈련·피아노·메트로놈, 화면 구성과 앱 설정을 검토했습니다.
- 기존 자동 검사 **129개 통과 / 실패 0 / 건너뜀 0**입니다.
- HTML ID·접근성 연결·정적 참조, JavaScript 문법, CSS 블록 구조, XML/JSON/PNG 검사도 통과했습니다.
- 추가로 실제 함수와 Java 소스를 대상으로 없는 음원, 손상된 복구 정보, 짧은 녹음, 긴 그래프, 분석 전달 대기를 모의 재현했습니다.
- 이번 작업은 검토이며 **프로젝트 소스는 변경하지 않았습니다.**
- Android SDK APK 빌드, 실제 WebView 화면 렌더링, 휴대폰 마이크·스피커·블루투스 검사는 수행하지 않았습니다. Java 재현에는 작은 Android API 대체 객체를 사용했습니다.

## 2. 확인된 문제와 재현 근거

### 2-1. 복구 정보 손상 시 목록에서 조용히 누락

관련: `app/src/main/java/com/voiceline/app/NativeWavStore.java:115`, `:132`, `:139`

`pending()`은 복구 파일의 모든 예외를 무시합니다. 녹음 중이어서 아직 열지 못하는 경우와 보조 정보 손상을 구분하지 않습니다.

실제 저장소 코드로 16kHz·1초 WAV를 만든 뒤, 보조 정보의 `rate` 값만 잘못된 문자열로 바꿨습니다.

| 확인 | 결과 |
|---|---|
| 손상 전 복구 목록 | 녹음 표시 |
| 손상 후 복구 목록 | 빈 목록 |
| WAV 존재 | 유지 |
| WAV 크기 | 32,044바이트 유지 |

개선 방향은 녹음 중인 파일만 일시 제외하고, 손상·접근 실패는 별도 상태로 보여주는 것입니다. 헤더가 유효한 WAV에서는 표본 속도와 길이를 다시 읽어 복구 정보를 만들 수 있습니다. 원본은 복구가 확인될 때까지 보존해야 합니다.

### 2-2. 외부 보관과 공유 기능 누락

관련: `NativeMicBridge.java:44`, `NativeWavStore.java:15`, `AndroidManifest.xml:5`, `piano.js:2827`

현재 WAV는 앱 내부 `files/voiceline-recordings`에 저장되고, 녹음 목록에는 전체 재생·삭제만 있습니다. 공유·외부 파일 저장·백업/가져오기 경로는 없습니다. Manifest의 백업 설정은 `allowBackup=false`입니다.

Android 공식 문서에 따르면 앱 전용 파일은 앱을 제거할 때 삭제됩니다. 따라서 사용자가 녹음을 계속 보관하려면 앱 밖으로 저장할 수단이 필요합니다.[1]

권장 흐름:

1. 녹음 목록에서 '파일로 저장'으로 시스템 저장 창을 엽니다.
2. 사용자가 폴더와 이름을 정하고 WAV를 복사합니다. 저장 성공 전에는 완료로 표시하지 않습니다.
3. '공유'는 사용자가 선택한 앱에 임시 읽기 권한을 주는 방식으로 제공합니다.
4. 앱 안의 원본은 유지합니다.

파일 저장은 Storage Access Framework의 `ACTION_CREATE_DOCUMENT`, 앱 내부 파일의 공유는 `FileProvider`와 읽기 권한 방식으로 구현할 수 있습니다.[1][2]

WAV 내보내기는 음성 보관 기능입니다. 녹음 제목·연습 결과·설정까지 새 기기로 옮기려면 별도의 백업/가져오기 기능이 필요합니다.

### 2-3. 포함 파일과 맞지 않는 예비 피아노 경로

관련: `piano.js:408`, `:430`, `:436`, `:465`, `:478`

배포 파일에는 `vendor/salamander`의 MP3 28개가 있지만, 이전 예비 로더는 `./samples/piano/INSPiano_Vel01_C4_01.ogg` 같은 주소를 요청합니다. 해당 파일은 없습니다.

실제 로더에 404 응답을 넣은 결과:

- 요청 파일: 존재하지 않는 OGG 경로
- 이전 상태 문구: '기본 음색 사용 · 음원 오류'
- 예비 로더 처리 후: '피아노 음원 일부 미지원'

주 엔진의 상태 표시를 다른 로더가 덮어씁니다. 예비 경로를 포함 MP3와 맞추거나 합성음으로 정리하고, 준비/실패/재시도 문구는 한 곳에서 관리하는 것이 좋습니다. 이 조건만으로 피아노 소리가 전혀 나지 않는다고 단정하지는 않습니다.

### 2-4. 짧은 녹음의 그래프와 진행 막대

관련: `piano.js:2842`, `:2865`, `:2866`, `:2901`, `:2906`

곡선의 시간 범위는 최소 1초, 재생선은 실제 길이 기준입니다. 길이 0.5초, 마지막 음정 500ms, 캔버스 폭 600px인 조건에서 실제 함수를 실행했습니다.

| 표시 | 끝의 X 위치 |
|---|---:|
| 음정 곡선 | 330.5px |
| 재생 위치선 | 592px |
| 차이 | 261.5px |

재생 슬라이더도 `Math.max(1, duration)`을 사용하므로 0.5초 파일의 끝이 전체 범위 중간에 해당합니다. 곡선·재생선·슬라이더를 같은 실제 길이로 맞추고 1초 미만 길이는 소수점으로 표시하는 것이 좋습니다. 녹음 오디오가 나뉘는 문제와는 별개의 표시 오류입니다.

### 2-5. 긴 녹음 재생 그래프의 반복 계산

관련: `piano.js:2851`, `:2863`, `:2908`

재생 중 약 90ms 이상 간격으로 전체 음정 자료를 필터링하고, 음역을 계산하고, 새 배열을 만든 뒤 곡선을 그립니다. 실제 함수에 40,000개 점을 넣어 10번 그렸을 때 필터 방문 400,000회와 변환 방문 400,000회를 확인했습니다.

화면 크기·자료가 바뀔 때만 배경 곡선을 계산하고, 재생선은 별도 레이어에서 갱신하는 것이 좋습니다. 화면 픽셀 수에 맞게 점을 줄일 때는 무음 구간과 음역의 최저·최고 변화가 유지되어야 합니다. 이 검사는 반복 작업 수를 확인한 것이며 휴대폰 프레임 저하를 측정한 결과는 아닙니다.

### 2-6. 네이티브 분석 메시지 제한의 범위

관련: `NativeMicBridge.java:146`, `:149`, `:150`, `:189`

대기 수 3개 제한은 UI 스레드의 전송 요청에 적용됩니다. `evaluateJavascript()`를 호출한 직후 대기 수를 줄이고, JavaScript 실행 완료는 확인하지 않습니다. Android 공식 문서에서 이 API는 비동기 실행이며 완료 결과를 콜백으로 받을 수 있습니다.[3]

실제 브리지 코드를 API 대체 객체와 함께 실행해, JavaScript는 실행하지 않고 UI 전송만 즉시 처리하는 조건을 만들었습니다. 분석 메시지 20개가 전달되었고, 음성 20,480프레임은 파일에 저장되었습니다.

소스와 이 모형 결과를 바탕으로, JavaScript 처리가 늦을 때 대기 자료가 3개 안에 제한된다고 보장할 수 없다고 판단했습니다. 실제 기기의 대기열 누적량·지연은 미측정입니다.

분석 완료 확인, 세션별 오래된 자료 폐기, 최신 분석 자료 중심 처리를 검토할 만합니다. 오디오 저장과 분석을 분리해 한 파일에 쓰는 현재 구조는 유지해야 합니다. 오래된 브리지의 PCM 저장 경로에는 같은 폐기 정책을 무조건 적용하면 안 됩니다.

## 3. 사용성과 추가 기능

### 녹음 관리

- 녹음 제목이 '목소리 녹음'으로 동일하므로 이름 변경과 검색을 제공하면 찾기 쉬워집니다.
- 현재 용량은 KB 고정입니다. 큰 WAV는 MB/GB로 표시하는 것이 읽기 좋습니다.
- 공유·파일 저장·이름 변경은 녹음 항목의 더보기 메뉴에 모으면 가로 화면에 버튼이 과하게 늘어나는 일을 줄일 수 있습니다.
- 현재 삭제 확인창과 녹음/연습 구분은 유지하는 편이 좋습니다.

### 저장 공간

현재 저장 실패 후 중단/복구 처리는 있으나 남은 공간을 미리 조회하는 기능은 없습니다. 44.1kHz·16비트·모노 WAV는 1시간 약 318MB입니다. 현재 표본 속도로 예상 시간을 계산해 녹음 화면이나 기록 화면에 간단히 보여주는 것이 좋습니다.

### 호흡·워밍업

현재 4초 들이쉬기 → 6초 내쉬기 → 6초 허밍 → 3초 쉬기는 고정입니다. 차후 단계별 시간과 안내음 켜기/끄기를 별도 설정창에서 제공하면 실용적입니다. 화면과 소리 안내가 같은 설정을 참조하도록 먼저 시간 상수를 통합하는 것이 좋습니다.

### 가로 화면·글꼴

설명 버튼 위치와 기본 강세 복원 버튼은 Local38에 반영되어 있습니다. 실제 글꼴 확대와 키보드 표시에서의 잘림·스크롤은 기기 검증이 필요합니다. 보이는 스크롤을 감추는 방식보다 핵심 조작을 유지하고 부가 정보를 정리하는 방향을 권합니다.

## 4. 불필요한 코드와 구조 정리

| 대상 | 확인한 내용 | 정리 방향 |
|---|---|---|
| 예전 OGG 경로·보정표·주석 | 현재 포함 MP3와 맞지 않는 예비 경로가 존재 | 예비 음색 정책을 정한 뒤 관련 코드를 함께 정리 |
| `ACOUSTIC_SAMPLE_MIDI` | 선언 뒤 참조가 없음 | 사용하지 않는 상수 제거 |
| 예전 워밍업 캔버스 분기 | `renderTrainingOverlay()`가 워밍업에서 먼저 반환한 뒤 아래에 예전 워밍업 분기가 남아 있음 | 도달하지 않는 분기와 전용 조건 정리 |
| 훈련 상태값 | `lastPlayed`, `relativeChanges`, `clicks`, `done` 등은 초기화 뒤 읽기 참조가 없음 | 불필요한 값 제거 |
| 사용하지 않는 음량 누적값 | `latestRms`, `totalRms`, `rmsMin` 등이 판정/표시에서 읽히지 않음 | 실제 쓰는 통계만 유지 |
| 워밍업 시간 | `WARMUP_CYCLE_MS` 외에 `19000` 직접 사용이 남아 있음 | 안내·시간·결과 계산에서 같은 상수 사용 |
| 핵심 JavaScript | `piano.js` 3,001줄에 저장·화면·오디오·훈련이 모여 있음 | 녹음/저장, 훈련, 기록 화면, 피아노 엔진 순으로 점진 분리 |
| CSS와 배포 문서 | 여러 버전의 덮어쓰기 규칙과 변경 안내가 누적됨 | 동작 확인 후 모드·화면 크기별 규칙과 문서를 정리 |

정리 작업에서도 기존 Blob 녹음 재생, 예전 임시 PCM 복구, 기록 마이그레이션은 유지해야 합니다. 이전 버전 데이터의 보존에 필요한 코드입니다. 음원 라이선스 자료와 원본 아이콘도 유지해야 합니다.

## 5. 코드·검사에서 확인한 기존 개선

- 녹음 파일과 연습 기록은 별도 탭으로 관리합니다.
- 현재 Android 녹음은 한 WAV에 순서대로 쓰고 마지막 입력 저장 확인을 기다립니다.
- 임의의 10분 제한과 자동 파일 분할은 없습니다. 앱 이탈·입력/저장 오류 시 종료하는 현재 정책은 유지됩니다.
- 저장 실패 재시도와 이전 녹음 자료의 복구 경로가 있습니다.
- 메트로놈의 BPM·음량·음소거·소리 변경은 현재 박을 유지합니다.
- 지나치게 빠른 메트로놈 조합은 거부됩니다. 예전 보고서의 초당 960회 조합은 Local38에서 오실레이터를 만들지 않는 것을 재확인했습니다.
- 메트로놈 설정 즐겨찾기, 직접 설정, 기본 화면의 강세 복원 버튼이 있습니다.
- 워밍업의 허밍 시작·종료 화면과 안내음이 있습니다.

이는 소스와 자동 검사 범위에서 확인한 내용입니다. 실제 기기에서의 녹음 품질과 화면 배치를 모두 검증했다는 뜻은 아닙니다.

## 6. 실기기에서 확인할 순서

주 기기인 Galaxy S24 Ultra / Android 16을 기준으로 다음을 확인하는 것이 좋습니다.

1. 10~30분 녹음, 시작/끝 음절과 무음 포함 여부, 실제 저장된 WAV 전체 재생.
2. 저장 공간 부족과 앱 중단 후 다시 저장/삭제, 손상된 보조 정보의 표시.
3. 기본·확대 글꼴의 가로 화면과 키보드 표시 상태, 설명/복원 버튼 접근.
4. 메트로놈·워밍업 중 전화·오디오 중단·블루투스 변경·앱 이탈 시 동작.
5. 리듬 훈련을 스피커/이어폰 각각 사용할 때 안내음이 마이크 판정에 끼치는 영향.
6. 기존 서명으로 업데이트한 뒤 예전 Blob·PCM 복구·현재 WAV 기록의 보존.
7. 내보내기를 추가한 뒤 큰 파일 저장, 취소·실패 처리, 공유 앱에서 파일 열기.

## 7. 권장 작업 순서

1. 복구 목록의 손상 정보 예외 처리와 WAV 기반 복구를 보완합니다.
2. 녹음 파일 저장·공유를 추가하고 완료/취소/실패 상태를 연결합니다.
3. 예비 피아노 경로와 짧은 녹음 시간축·진행 막대를 수정합니다.
4. 긴 그래프 캐시와 분석 대기 제어, 저장 공간 안내를 보완합니다.
5. 녹음 이름·검색·용량 표기, 워밍업 설정을 정리합니다.
6. 사용하지 않는 코드와 누적 스타일을 정리하고 실제 Android 빌드·기기 검증으로 마무리합니다.
